\chapter[ANÁLISIS Y DISEÑO]{Análisis y diseño}
\label{cap:analisis-diseno}

El análisis consiste en identificar qué debe ocurrir dentro del sistema y cómo se relacionarán
entre sí los distintos procesos que lo conforman, lo que permite entender el problema y documentar
las relaciones entre los usuarios, el programa y los componentes que integran la lógica del
sistema antes de escribir cualquier línea de código \cite{pressman2010}. En el caso del presente
trabajo, esta etapa corresponde a las fases de definición de requerimientos y de diseño de la
arquitectura del modelo incremental descrito en el Capítulo~\ref{cap:propuesta}, y se orienta a
describir, mediante requerimientos y diagramas, el comportamiento esperado de la interfaz del P300
Speller, de la adquisición y calibración con el casco EEG, del módulo de detección de la
componente P300 y del módulo de predicción de palabras,
combinando el lenguaje del usuario con el enfoque técnico de quien desarrolla el sistema.

Por otra parte, el diseño se encarga de traducir dicho análisis en decisiones concretas de
implementación: a partir de los requerimientos y los diagramas generados se define cómo se
organizará el código en módulos, cómo se intercambiará la información entre la interfaz, el
modelo de aprendizaje profundo y el modelo de lenguaje, qué datos deberán almacenarse, así como la
plataforma en la que se ejecutará cada componente y los recursos que requerirá \cite{pressman2010}.

\section[REQUERIMIENTOS]{Requerimientos}

Los requerimientos funcionales establecen lo que el sistema debe hacer, es decir, los servicios que
ofrece y la forma en que responde a cada entrada, mientras que los requerimientos no funcionales
describen atributos de calidad con los que el sistema debe cumplir esos servicios, como su
rendimiento, usabilidad, confiabilidad, seguridad o mantenibilidad, sin constituir por sí mismos una
función del sistema \cite{pressman2010}. Cabe señalar que la exploración de arquitecturas con
bases de datos públicas y la selección de la configuración del modelo se efectúan de manera previa
por parte de quienes desarrollan el sistema, como se describe en la
Sección~\ref{sec:flujo-entrenamiento}, por lo que no forman parte de lo que la aplicación ofrece a
la persona que la utiliza. En cambio, el entrenamiento del modelo de cada usuario sí se realiza
dentro de la aplicación, al concluir su calibración.

\subsection{Requerimientos funcionales}

Los requerimientos funcionales se agrupan según el módulo del sistema al que corresponden: la
gestión de cuentas y mensajes, la adquisición de señales y la calibración, el deletreo mediante el
paradigma P300 Speller y la predicción de palabras.

\paragraph{Gestión de cuentas y mensajes.}

\begin{itemize}
  \item \textbf{RF1:} El sistema deberá permitir al operador crear la cuenta de un usuario.
  \item \textbf{RF2:} El sistema deberá permitir iniciar sesión con una cuenta existente, de modo
  que cada usuario acceda únicamente a su propia información.
  \item \textbf{RF3:} El sistema deberá permitir cerrar la sesión activa.
  \item \textbf{RF4:} El sistema deberá guardar los mensajes construidos en la cuenta del usuario
  que los escribió y permitirle consultarlos posteriormente.
\end{itemize}

\paragraph{Adquisición de señales y calibración.}

\begin{itemize}
  \item \textbf{RF5:} El sistema deberá conectarse al casco EEG y recibir de forma continua las
  señales de sus canales durante la calibración y el deletreo.
  \item \textbf{RF6:} El sistema deberá registrar el instante y el tipo de cada intensificación
  presentada, es decir, la fila o columna iluminada, para asociar cada época de EEG con el
  estímulo que la provocó.
  \item \textbf{RF7:} El sistema deberá mostrar el estado de la señal de cada canal del casco y
  permitir verificar su calidad antes de iniciar una calibración o una sesión de deletreo.
  \item \textbf{RF8:} El sistema deberá contar con un modo de calibración en el que se indique al
  usuario el carácter en el que debe fijar su atención, se presenten las secuencias de
  estimulación y se registren las señales correspondientes, el cual podrá repetirse cuando sea
  necesario actualizar el modelo del usuario.
  \item \textbf{RF9:} El sistema deberá guardar los registros de cada sesión de calibración, junto
  con los caracteres objetivo y los eventos de estimulación, en la cuenta del usuario que los
  generó.
  \item \textbf{RF10:} El sistema deberá entrenar de forma automática, al concluir la calibración,
  el modelo de detección del usuario a partir de sus registros, empleando la arquitectura y la
  configuración seleccionadas previamente, y guardarlo en su cuenta junto con el número de
  repeticiones por selección y los tiempos de intensificación empleados en dicha calibración.
  \item \textbf{RF11:} El sistema deberá evaluar el modelo entrenado con una parte de los registros
  de calibración reservada para ese fin y, si su exactitud por carácter no alcanza el valor mínimo
  establecido, informarlo y proponer que se repita la calibración.
  \item \textbf{RF12:} El sistema deberá cargar, al iniciar sesión, el modelo de detección
  entrenado para ese usuario, junto con el número de repeticiones por selección y los tiempos de
  intensificación asociados a dicho modelo, de modo que el deletreo se realice con los mismos
  parámetros empleados en su calibración, e impedir que inicie el deletreo si la cuenta aún no
  cuenta con un modelo.
\end{itemize}

\paragraph{Deletreo mediante el P300 Speller.}

\begin{itemize}
  \item \textbf{RF13:} El sistema deberá mostrar una interfaz gráfica con una matriz de selección
  de $6\times6$ elementos que contenga las letras del alfabeto en español, el espacio y el comando
  de borrado.
  \item \textbf{RF14:} El sistema deberá intensificar de manera aleatoria las filas y columnas de
  la matriz durante cada secuencia de estimulación.
  \item \textbf{RF15:} El sistema deberá preprocesar las señales recibidas del casco, aplicando el
  filtrado, la segmentación en épocas a partir de cada intensificación y la normalización.
  \item \textbf{RF16:} El sistema deberá clasificar cada época como objetivo o no objetivo con el
  modelo de detección del usuario, asignándole un puntaje de probabilidad.
  \item \textbf{RF17:} El sistema deberá determinar el elemento seleccionado a partir de la
  acumulación de los puntajes de cada fila y cada columna a lo largo de las repeticiones.
  \item \textbf{RF18:} El sistema deberá mostrar en la interfaz el texto construido por el usuario
  y actualizarlo después de cada selección.
  \item \textbf{RF19:} El sistema deberá permitir borrar el último carácter o la última palabra
  seleccionados mediante un elemento de la matriz.
\end{itemize}

\paragraph{Predicción de palabras.}

\begin{itemize}
  \item \textbf{RF20:} El sistema deberá generar sugerencias de palabras a partir de los
  caracteres escritos hasta ese momento.
  \item \textbf{RF21:} El sistema deberá presentar las sugerencias como elementos seleccionables y
  permitir elegirlas mediante el mismo mecanismo de estimulación y detección de la componente
  P300 que se emplea para los caracteres.
\end{itemize}

\subsection{Requerimientos no funcionales}

\begin{itemize}
  \item \textbf{RNF1 (rendimiento):} Una vez concluida la última repetición de una selección, el
  elemento seleccionado deberá mostrarse en la interfaz en un tiempo no mayor a un segundo, y las
  sugerencias de palabras deberán actualizarse antes de que inicie la siguiente secuencia de
  estimulación.
  \item \textbf{RNF2 (usabilidad):} La matriz deberá presentarse con un tamaño de carácter y un
  contraste que permitan al usuario fijar su atención en cualquier elemento sin esfuerzo visual
  excesivo, y los elementos intensificados deberán distinguirse claramente de los que no lo están.
  \item \textbf{RNF3 (accesibilidad):} Una vez iniciada la sesión de deletreo, todas las acciones de
  escritura, selección de sugerencias y borrado deberán poder realizarse únicamente mediante la
  atención a la matriz, sin requerir teclado ni ratón.
  \item \textbf{RNF4 (usabilidad):} La sesión de calibración deberá poder completarse en un tiempo
  no mayor a 15 minutos, con el fin de limitar la fatiga del usuario, y durante el entrenamiento
  automático del modelo la interfaz deberá mostrar su avance sin dejar de responder.
  \item \textbf{RNF5 (confiabilidad):} Si se pierde la conexión con el casco durante una sesión, el
  sistema deberá detener la estimulación, notificarlo al usuario y conservar el texto construido
  hasta ese momento.
  \item \textbf{RNF6 (seguridad):} Las contraseñas de los usuarios deberán guardarse en el
  almacenamiento local del sistema como un resumen criptográfico (\textit{hash}) y nunca en texto
  plano, de modo que no puedan leerse aun cuando se acceda directamente a los archivos del equipo.
  \item \textbf{RNF7 (privacidad):} La aplicación deberá mostrar a cada usuario únicamente sus
  propios mensajes, y los registros EEG deberán guardarse identificados solo con el identificador de
  la cuenta, sin nombre ni otros datos personales, de modo que no revelen la identidad del usuario
  si se consultan o copian fuera de la aplicación.
  \item \textbf{RNF8 (mantenibilidad):} El sistema deberá tener una arquitectura modular que
  permita reemplazar el modelo de detección o el modelo de predicción de palabras sin modificar la
  interfaz.
  \item \textbf{RNF9 (portabilidad):} La adquisición de señales deberá encapsularse en un módulo
  independiente, de modo que el casco pueda sustituirse por otro dispositivo de EEG modificando
  únicamente dicho módulo, y la inferencia del modelo deberá poder ejecutarse por separado de la
  interfaz para facilitar su traslado a otro equipo.
\end{itemize}

Los diagramas de flujo describen la secuencia de pasos de los procesos más importantes del sistema,

\subsection{Preprocesamiento de las señales EEG}

El preprocesamiento aplica a las señales las técnicas descritas en la Sección~\ref{sec:pds}, entre

y la normalización de cada canal, y es común tanto al flujo de entrenamiento como al de uso del
sistema, de modo que el modelo recibe en ambos casos datos con el mismo formato, ya provengan de las bases de datos públicas o
del casco EEG. Los valores
específicos de cada parámetro se definirán durante el diseño experimental.

\subsection{Entrenamiento y evaluación del modelo de detección}
\label{sec:flujo-entrenamiento}

El entrenamiento y la evaluación del modelo de detección de la componente P300 constan de dos
etapas. La primera, de exploración, se realiza antes y fuera de la aplicación, por parte del
operador, siguiendo las fases de la metodología CRISP-ML descritas en el
Capítulo~\ref{cap:propuesta}. En ella se preparan los datos de las bases públicas, se entrenan las
arquitecturas candidatas y se evalúa su desempeño con las métricas de clasificación revisadas en la
Sección~\ref{sec:metricas}, bajo esquemas de validación intrasujeto e intersujeto, así como el
efecto de reducir el número de canales y de repeticiones, con el fin de seleccionar la arquitectura
y la configuración del modelo. La segunda etapa se realiza dentro de la aplicación al concluir la
calibración de cada usuario. Sus registros se preprocesan con el mismo flujo de la sección
anterior, se separa una parte de ellos para la validación y con el resto se entrena la arquitectura
seleccionada. Si la exactitud por carácter obtenida en la validación alcanza el valor mínimo
establecido, el modelo se guarda en la cuenta del usuario y se habilita el deletreo, y en caso
contrario se propone repetir la calibración.

\subsection{Decodificación del carácter seleccionado}

La decodificación recorre las repeticiones de una selección: en cada una se intensifican las filas
y columnas de la matriz, se clasifican las épocas resultantes y se acumulan los puntajes por fila y
por columna, de acuerdo con la Ecuación~\eqref{eq:decodificacion}, hasta que se completa el número
de repeticiones y se elige el elemento ubicado en la intersección de la fila y la columna con el
puntaje más alto.

\section[DISEÑO DEL MÓDULO DE PREDICCIÓN DE PALABRAS]{Diseño del módulo de predicción de palabras}

El módulo de predicción de palabras recibe los caracteres escritos hasta el momento y devuelve una
lista breve de palabras probables, que la interfaz presenta como opciones adicionales y que el
usuario puede elegir con el mismo mecanismo de atención que emplea para los caracteres. En esta
sección se define la información que intercambia el módulo con el resto del sistema y la forma en
que se presentan y seleccionan las sugerencias, dejando para el Capítulo~5 la elección del modelo
de lenguaje concreto entre los enfoques revisados en la Sección~\ref{sec:lenguaje}.
