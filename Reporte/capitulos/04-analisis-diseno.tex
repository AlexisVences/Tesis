\chapter[ANÁLISIS Y DISEÑO]{Análisis y diseño}
\label{cap:analisis-diseno}

El análisis consiste en identificar qué debe ocurrir dentro del sistema y cómo se relacionarán
entre sí los distintos procesos que lo conforman, lo que permite entender el problema y documentar
las relaciones entre los usuarios, el programa y los componentes que integran la lógica del
sistema antes de escribir cualquier línea de código \cite{pressman2010}. En el caso del presente
trabajo, esta etapa corresponde a las fases de definición de requerimientos y de diseño de la
arquitectura del modelo incremental descrito en el Capítulo~\ref{cap:propuesta}, y se orienta a
describir, mediante requerimientos y diagramas, el comportamiento esperado de la interfaz del P300
Speller, de la adquisición y calibración con el casco EEG, del módulo de detección de la
componente P300 y del módulo de predicción de palabras,
combinando el lenguaje del usuario con el enfoque técnico de quien desarrolla el sistema.

Por otra parte, el diseño se encarga de traducir dicho análisis en decisiones concretas de
implementación: a partir de los requerimientos y los diagramas generados se define cómo se
organizará el código en módulos, cómo se intercambiará la información entre la interfaz, el
modelo de aprendizaje profundo y el modelo de lenguaje, qué datos deberán almacenarse, así como la
plataforma en la que se ejecutará cada componente y los recursos que requerirá \cite{pressman2010}.

Las reglas de negocio son las condiciones y restricciones propias del dominio que el sistema debe
respetar sin importar la forma en que se implemente, y de ellas se desprenden tanto los

una persona, conservando cada una su modelo de detección y sus registros de manera independiente, y las reglas consideradas se

\section[REQUERIMIENTOS]{Requerimientos}

Los requerimientos funcionales establecen lo que el sistema debe hacer, es decir, los servicios que
ofrece y la forma en que responde a cada entrada, mientras que los requerimientos no funcionales
describen atributos de calidad con los que el sistema debe cumplir esos servicios, como su
rendimiento, usabilidad, confiabilidad, seguridad o mantenibilidad, sin constituir por sí mismos una
función del sistema \cite{pressman2010}. Cabe señalar que la exploración de arquitecturas con
bases de datos públicas y la selección de la configuración del modelo se efectúan de manera previa
por parte de quienes desarrollan el sistema, como se describe en la
Sección~\ref{sec:flujo-entrenamiento}, por lo que no forman parte de lo que la aplicación ofrece a
la persona que la utiliza. En cambio, el entrenamiento del modelo de cada usuario sí se realiza
dentro de la aplicación, al concluir su calibración.

\subsection{Requerimientos funcionales}

Los requerimientos funcionales se agrupan según el módulo del sistema al que corresponden: la
gestión de cuentas, la adquisición de señales y la calibración, el deletreo mediante el
paradigma P300 Speller y la predicción de palabras.

\paragraph{Gestión de cuentas.}

\begin{itemize}
  \item \textbf{RF1:} El sistema deberá permitir al operador crear la cuenta de un usuario.
  \item \textbf{RF2:} El sistema deberá permitir al operador iniciar sesión con la cuenta existente de un usuario, de modo
  que cada usuario acceda únicamente a su propia información.
  \item \textbf{RF3:} El sistema deberá permitir al operador cerrar la sesión activa.
\end{itemize}

\paragraph{Adquisición de señales y calibración.}

\begin{itemize}
  \item \textbf{RF4:} El sistema deberá permitir al operador establecer la conexión con el casco EEG y, a partir de ella, recibir de forma continua las
  señales de sus canales durante la calibración y el deletreo.
  \item \textbf{RF5:} El sistema deberá registrar el instante y el tipo de cada intensificación
  presentada, es decir, la fila o columna iluminada, para asociar cada época de EEG con el
  estímulo que la provocó.
  \item \textbf{RF6:} El sistema deberá mostrar el estado de la señal de cada canal del casco y
  permitir al operador verificar su calidad antes de iniciar una calibración o una sesión de deletreo.
  \item \textbf{RF7:} El sistema deberá permitir al operador iniciar un modo de calibración en el que se indique al
  usuario el carácter en el que debe fijar su atención, se presenten las secuencias de
  estimulación y se registren las señales correspondientes, el cual podrá repetirse por indicación del operador cuando sea
  necesario actualizar el modelo del usuario. 
  \item \textbf{RF8:} El sistema deberá guardar los registros de cada sesión de calibración, junto
  con los caracteres objetivo y los eventos de estimulación, en la cuenta del usuario que los
  generó.
  \item \textbf{RF9:} El sistema deberá entrenar de forma automática, al concluir la calibración, el modelo de detección del usuario a partir de sus registros, empleando la arquitectura y la configuración seleccionadas previamente, guardarlo en su cuenta y mostrar su avance al operador durante el proceso.
  \item \textbf{RF10:} El sistema deberá evaluar el modelo entrenado con una parte de los registros
  de calibración reservada para ese fin y, si su exactitud por carácter no alcanza el valor mínimo
  establecido, informarlo y proponer que se repita la calibración.
  \item \textbf{RF11:} El sistema deberá cargar, al iniciar sesión, el modelo de detección
  entrenado para ese usuario y permitir al operador iniciar el deletreo, impidiéndolo si la cuenta aún no tiene un modelo.
\end{itemize}

\paragraph{Deletreo mediante el P300 Speller.}

\begin{itemize}
  \item \textbf{RF12:} El sistema deberá mostrar una interfaz gráfica con una matriz de selección
  de $6\times6$ elementos que contenga las letras del alfabeto en español, el espacio y el comando de borrado, y cuyos elementos restantes se destinen a las sugerencias de palabras.
  \item \textbf{RF13:} El sistema deberá intensificar de manera aleatoria las filas y columnas de
  la matriz durante cada secuencia de estimulación.
  \item \textbf{RF14:} El sistema deberá preprocesar las señales recibidas del casco, aplicando el
  filtrado, la segmentación en épocas a partir de cada intensificación y la normalización.
  \item \textbf{RF15:} El sistema deberá clasificar cada época como objetivo o no objetivo con el
  modelo de detección del usuario, asignándole un puntaje de probabilidad.
  \item \textbf{RF16:} El sistema deberá determinar el elemento seleccionado a partir de la
  acumulación de los puntajes de cada fila y cada columna a lo largo de las repeticiones.
  \item \textbf{RF17:} El sistema deberá mostrar en la interfaz el texto construido por el usuario
  y actualizarlo después de cada selección.
  \item \textbf{RF18:} El sistema deberá permitir borrar el último carácter o la última palabra
  seleccionados mediante un elemento de la matriz.
\end{itemize}

\paragraph{Predicción de palabras.}

\begin{itemize}
  \item \textbf{RF19:} El sistema deberá generar sugerencias de palabras a partir de los
  caracteres escritos hasta ese momento.
  \item \textbf{RF20:} El sistema deberá presentar las sugerencias como elementos seleccionables y
  permitir elegirlas mediante el mismo mecanismo de estimulación y detección de la componente
  P300 que se emplea para los caracteres.
\end{itemize}

\subsection{Requerimientos no funcionales}

\begin{itemize}
  \item \textbf{RNF1:} Una vez concluida la última repetición de una selección, el
  elemento seleccionado deberá mostrarse en la interfaz en un tiempo no mayor a un segundo, y las
  sugerencias de palabras deberán actualizarse antes de que inicie la siguiente secuencia de
  estimulación.
  \item \textbf{RNF2:} La matriz deberá presentarse con un tamaño de carácter y un
  contraste que permitan al usuario fijar su atención en cualquier elemento sin esfuerzo visual
  excesivo, y los elementos intensificados deberán distinguirse claramente de los que no lo están.
  \item \textbf{RNF3:} Una vez iniciada la sesión de deletreo, todas las acciones de
  escritura, selección de sugerencias y borrado deberán poder realizarse únicamente mediante la
  atención a la matriz, sin requerir teclado ni ratón.
  \item \textbf{RNF4:} La sesión de calibración deberá poder completarse en un tiempo
  no mayor a 15 minutos, con el fin de limitar la fatiga del usuario, y durante el entrenamiento
  automático del modelo la interfaz deberá mostrar su avance sin dejar de responder.
  \item \textbf{RNF5:} Si se pierde la conexión con el casco durante una sesión, el
  sistema deberá detener la estimulación, notificarlo al usuario y conservar el texto construido
  hasta ese momento.
  \item \textbf{RNF6:} Las contraseñas de los usuarios deberán almacenarse de forma que no puedan leerse directamente en los archivos del equipo.
  \item \textbf{RNF7:} La aplicación deberá permitir consultar los registros EEG de cada usuario únicamente a él y al operador, y estos deberán guardarse identificados solo con el identificador de
  la cuenta, sin nombre ni otros datos personales, de modo que no revelen la identidad del usuario
  si se consultan o copian fuera de la aplicación.
  \item \textbf{RNF8:} El sistema deberá tener una arquitectura modular que
  permita reemplazar el modelo de detección o el modelo de predicción de palabras sin modificar la
  interfaz.
  \item \textbf{RNF9:} La adquisición de señales deberá realizarse en un módulo independiente, de modo que el casco pueda sustituirse por otro dispositivo de EEG modificando únicamente dicho módulo.
\end{itemize}

\section[CATÁLOGO DE MENSAJES]{Catálogo de mensajes}

El catálogo de mensajes reúne los avisos que el sistema presenta durante su operación, clasificados
según su propósito para que la interfaz mantenga un lenguaje uniforme en todas sus pantallas. Dado
que el usuario final interactúa principalmente mediante la selección de elementos con la
componente P300, los textos deberán ser breves y de lectura inmediata, e indicar en cada caso qué
ocurrió y, cuando proceda, qué debe hacerse a continuación.

\subsection{Mensajes de error}

Los mensajes de error informan que una operación no pudo completarse, ya sea porque los datos
proporcionados no son válidos, como al registrar una cuenta o iniciar sesión, o porque un recurso
necesario no está disponible, como el modelo de detección o la conexión con el casco EEG, o
porque el modelo entrenado no alcanza la exactitud mínima establecida.

\section[CASOS DE USO]{Casos de uso}

Los casos de uso representan las distintas funcionalidades del sistema y se definen a partir de los
requerimientos funcionales, de manera que cada uno describe una acción específica, junto con sus
precondiciones, pasos y posibles errores, que el sistema debe realizar para cumplir con las
necesidades de quienes interactúan con él \cite{pressman2010}. Los actores, por su parte, son los
roles que se asignan a las personas o a los sistemas externos que interactúan con dichas
funcionalidades, y en el presente trabajo intervienen el usuario que construye mensajes a través
del P300 Speller, el operador que prepara y supervisa las sesiones y el casco EEG que proporciona
las señales, tal como se describe en la Tabla~\ref{tab:actores}.

\section[DIAGRAMAS DE FLUJO]{Diagramas de flujo}

Los diagramas de flujo describen la secuencia de pasos de los procesos más importantes del sistema,
y se presentan aquí los tres que concentran la lógica del procesamiento de las señales y del
modelo: el preprocesamiento, el entrenamiento del modelo de detección y la decodificación del

\subsection{Preprocesamiento de las señales EEG}

El preprocesamiento aplica a las señales las técnicas descritas en la Sección~\ref{sec:pds}, entre
ellas el filtrado pasa banda, el remuestreo, la segmentación en épocas posteriores a cada estímulo
y la normalización de cada canal, y es común tanto al flujo de entrenamiento como al de uso del
sistema, de modo que el modelo recibe en ambos casos datos con el mismo formato, ya provengan de las bases de datos públicas o
del casco EEG. Los valores
específicos de cada parámetro se definirán durante el diseño experimental.

El flujo, que se muestra en la Figura~\ref{fig:flujo-preprocesamiento}, comienza con la recepción del registro, que puede provenir de una base de datos pública o del casco, y aplica en orden el filtro pasa banda, el remuestreo, la segmentación en épocas y la normalización de cada canal. Cuando los datos se emplean para entrenar, a cada época se le asigna además la etiqueta de objetivo o no objetivo según la fila o columna que se intensificó, mientras que durante el deletreo las épocas se entregan directamente al modelo, ya que se desconoce cuál es el carácter que el usuario desea seleccionar.

\subsection{Entrenamiento y evaluación del modelo de detección}
\label{sec:flujo-entrenamiento}

El entrenamiento y la evaluación del modelo de detección de la componente P300 que se representan en esta sección son los que realiza la aplicación para cada usuario al concluir su calibración. La arquitectura y la configuración del modelo se definen antes, durante su desarrollo con las bases de datos públicas y siguiendo las fases de la metodología CRISP-ML descritas en el Capítulo~\ref{cap:propuesta}, por lo que aquí se toman como un dato de entrada. La decodificación recorre las repeticiones de una selección: en cada una se intensifican las filas

de repeticiones y se elige el elemento ubicado en la intersección de la fila y la columna con el
puntaje más alto.

\section[DIAGRAMA DE ESTADOS]{Diagrama de estados}

La interfaz del P300 Speller cambia de comportamiento a lo largo de una sesión de deletreo, pues
alterna entre la presentación de las secuencias de estimulación, la clasificación de las épocas
registradas y la actualización del texto, a lo que se suman la conexión con el casco y la
calibración, y el diagrama de estados permite describir cada una de
estas situaciones junto con los eventos que provocan la transición de una a otra.

En la Figura~\ref{fig:estados} se identifican ocho estados principales. La sesión inicia sin usuario autenticado y, al iniciar sesión, pasa a una sesión activa desde la cual se llega directamente al estado de modelo listo si la cuenta ya tiene uno, o bien al de casco conectado cuando es necesario calibrar. A partir de este último se verifica la señal y se calibra, y al concluir la calibración se entrena el modelo, de modo que una validación aprobada conduce al estado de modelo listo y una no aprobada regresa al de casco conectado para repetir el proceso. El estado de deletreo contiene a su vez un ciclo de estimulación, clasificación y actualización del texto que se repite por cada selección hasta que el operador detiene el deletreo o cierra la sesión.
